# Confirmatory lock PROPOSAL (2026-11-17): concrete values for every bracket in PROPOSAL.md section 4

Status: PROPOSED, awaiting the Owner's tap. This file fills every
bracket left open by PROPOSAL.md section 4 and recorded as still
open in docs/decisions/0005-confirmatory-lock.md, with one concrete
value each and a one-line justification grounded in this repo's own
record. It does NOT lock anything by itself: PROPOSAL.md is not
edited, no entry is added to DECISIONS.md, nothing has been run,
and the proposal-v1 tag is not applied. On the Owner's approval, a
further decision entry records this design as settled and the tag
can be applied.

## The values

- Model: Qwen2.5-1.5B (base, open weights, Apache 2.0).
  Justification: the top of section 4's 0.5B to 1.5B range gives
  the H1 adapter-versus-full gap the most room to show; the base
  model (not the instruct variant) keeps the before and after
  measurement clean, and it is a standard subject for the TRL-class
  post-training recipes this repo names as its prior art
  (PROPOSAL.md section 3).

- Machine and budget: the Spark spark-6aa3 (NVIDIA GB10, 121 GiB
  unified memory, far above section 4's 24 GB floor), all work
  inside ~/Jesun_Gallea_Dev/finetune-lab on that machine. Budget:
  96 GPU-hours, a cap over a bottom-up estimate of about 81 hours
  (SFT arms about 32.5 h, GRPO arms about 15 h, DPO arms about
  10 h, PPO baseline about 10 h, plus about 20 percent for
  evaluation and failed-run contingency; per-run times are
  estimates, labelled as such, in line with REPORT.md's "a few
  GPU-hours per method (estimate)").

- Instruction set: Alpaca (tatsu-lab/alpaca, 52,002 examples),
  using a frozen 10,000-example training slice (seed 0 shuffle,
  fixed at the lock), with the next 1,000 examples as the
  validation slice for checkpoint selection and the next 1,000 as
  held-out. Justification: the canonical public instruction set
  for LoRA SFT in the recipe class the repo takes as prior art;
  the frozen slice keeps the 10-seed design inside the GPU-hour
  budget above.

- Math word-problem set: GSM8K (7,473 train, 1,319 test), scored
  by exact match on the final numeric answer. Justification: it is
  the public math word-problem set whose programmatic checker
  section 4 requires; GRPO trains on train-split prompts, DPO
  preference pairs are built from train-split prompts (chosen: the
  gold solution; rejected: a sampled completion whose final number
  fails the checker; the misaligned arm flips chosen and rejected
  on 50 percent of prompts, mirroring the post hoc design's 4 of 8
  misaligned prompts), and all held-out scoring uses the test
  split, never trained on.

- H1 pass line: the LoRA adapter's held-out accuracy (exact-match
  accuracy on the GSM8K test split after instruction SFT) lands
  within 5 points of full fine-tuning at matched budget.
  Justification: the post hoc gap was 3.52 points (adapter 0.9039
  against full 0.9391, 10-seed means, rigor/results_rigor.json),
  measured on a toy task whose target change was rank 2 by
  construction, which favours the adapter (REPORT.md section 7);
  the line is set at about 1.4 times the post hoc gap to allow for
  a real target change that is not rank 2.

- H2 criterion (no bracket in section 4; the verdict rule needs
  one): GRPO at beta in {0, 0.04, 0.1}; the trade-off holds if
  seed-mean final KL and seed-mean final reward both fall from
  beta 0 to beta 0.1, with beta 0.04 between them.
  Justification: 0.04 is the Build run's recorded beta, and 0 and
  0.1 are the post hoc sweep endpoints with measured values
  (reward 0.9637 and KL 1.1980 at beta 0; reward 0.8859 and KL
  0.9544 at beta 0.1, rigor grpo_beta_budget).

- H3 pass line: DPO on aligned preferences improves held-out
  preference accuracy (GSM8K test-prompt pairs, same construction
  as the training pairs) over the SFT reference by at least 25
  points. Justification: the post hoc gain was 56.25 points
  (0.4375 to 1.0000 on the recorded run, with held-out preference
  accuracy 1.0000 on all 10 seeds); the line is set at about 44
  percent of that gain, discounted because the post hoc
  preferences were generated by the same checker that scored them
  (REPORT.md section 7), so a real-data effect should be smaller.

- H4 pass line: DPO on misaligned preferences lowers accuracy on
  the retained task (GSM8K test exact-match accuracy, a capability
  the preference run never trains on) by at least 15 points
  against the same model's pre-DPO accuracy. Justification: the
  post hoc shared-weight drop was 28.75 points (0.5375 aligned to
  0.2500 with half the prompts misaligned, rigor
  misaligned_retention); the line is set at about half that drop.

- Seed count: 10 seeds per arm, bootstrap 95 percent intervals
  (10,000 resamples), every run reported, no seed dropped.
  Justification: this is the repo's own rigor standard (every
  rigor headline is a 10-seed mean with a bootstrap 95 percent
  interval), so the confirmatory intervals stay directly
  comparable with the post hoc ones they test.

- Verdict rule: per hypothesis, applied to the seed-mean effect
  and its bootstrap 95 percent interval. CONFIRMED if the mean
  meets the pass line and the whole interval sits on the passing
  side of the line; REFUTED if the mean fails the line and the
  whole interval sits on the failing side; INCONCLUSIVE when the
  interval crosses the line. For H2, CONFIRMED requires both
  orderings (KL down, reward down) in the seed means with both
  difference intervals excluding zero; REFUTED if either ordering
  reverses with its interval excluding zero; INCONCLUSIVE
  otherwise. Justification: it is the three-way rule the
  portfolio's other locked studies use, and it makes an interval
  that straddles a line an honest INCONCLUSIVE rather than a
  verdict bought by a point estimate.

- Epochs: 3, for both H1 arms, with best-validation checkpoint
  selection. Justification: the rigor pass showed best-validation
  selection lifts the adapter's 10-seed mean from 0.9039 to
  0.9219, so with the selection rule registered, a third epoch
  gives the rule a peak to find instead of shipping a final-epoch
  adapter; matched budget means both arms share the data slice,
  the epoch count, and the selection rule.

- Adapter learning rate: 1e-3 for the LoRA arm. Justification:
  adapters in the TRL-class recipes this repo takes as prior art
  train at about 1e-3, an order above full-model rates; the
  alternative 5e-4 risks an undertrained adapter, which would
  decide H1 on optimization rather than on adapter capacity (the
  full fine-tune arm keeps its own standard full-model rate under
  the same matched-budget definition).

- Masking convention for the H1 arms: completion-only (loss on
  response tokens only; prompt tokens masked), in both arms.
  Justification: it is the standard SFT convention in the
  TRL-class recipes named as prior art, and it keeps the H1
  comparison about the response distribution both arms must
  learn, not about prompt modelling.

## What stays as section 4 wrote it

Baselines under the same budget: full fine-tune (the H1 arm
itself) and PPO with a critic on the same model and task (one
further arm, 10 seeds). Every run is reported. No hypothesis,
pass line, or analysis choice above may be changed after the
first confirmatory run starts; changes after that point go in a
dated amendment, never in this file retroactively.
