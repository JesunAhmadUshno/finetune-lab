# Level 2, Build: finetune-lab

Status: DONE (2026-11-05, early, Sprint 3 pull). A full fine-tune
pipeline (data prep, SFT-style LoRA training, checkpoint save and
load, eval harness with before and after numbers) plus a GRPO
track that trains a toy policy with a clipped surrogate loss and
a KL term, with measured reward improvement. All NumPy, all
synthetic, all on Muse VM CPU. See BUILD-SPEC.md for the scope
mapping and the one named SPEC gap.

## Summary claim (beside its measured table)

Build DONE: on synthetic NumPy tasks only, the SFT pipeline
(512 train, 128 validation, 128 held-out test, 4 classes, input
dim 16) trained a rank 2 LoRA adapter (40 trainable parameters
against 64 for full fine-tuning) with minibatch training
(batch 64, 60 epochs) and raised held-out test accuracy from
0.6797 (87 of 128) before training to 0.9141 (117 of 128) after,
with test loss from 1.0007 to 0.2032, the frozen base weights
unchanged, and a checkpoint round-trip that reproduces the after
numbers exactly; and the GRPO track trained a tabular toy policy
on 8 checker prompts (group size 8, clip eps 0.2, KL beta 0.04,
60 iterations) and raised fresh-sample mean reward from 0.2070
before to 0.9766 after, with greedy accuracy from 0.125 (1 of 8)
to 1.0000 (8 of 8); all on Muse VM CPU, with no real LLM, no
real text data, and no open model run.

## Reading the split honestly

The data stream is the Learn stream continued: 512 train, then
128 validation, then 128 test, all from data seed 7 in that
order. The validation slice is the slice Learn used as its test
set, which is why the before validation numbers (0.5469, loss
1.0707) match the Learn before test numbers exactly. The test
slice here is fresh held-out data Learn never scored on, which
is why the before test accuracy here (0.6797) differs from
Learn. Compare Build before and after inside this level, on the
same held-out slice. Do not compare Build test numbers against
Learn test numbers as if they were one set.

## The SFT pipeline (pipeline.py)

1. Data prep. make_dataset builds the task exactly as in Learn
   (target is the base plus a rank 2 change by construction) and
   splits it deterministically. data_card records counts and
   class balance per split: train 134, 121, 79, 178 across the
   four classes; validation 34, 28, 16, 50; test 30, 35, 10, 53.
   The class balance is uneven, which is why the harness reports
   per-class accuracy and a confusion matrix, not one number.
2. Training. Minibatch gradient descent, batch 64, 8 batches per
   epoch, 60 epochs, learning rate 0.5, shuffled per epoch with
   a seeded generator. Only adapter A and B update. The base
   hash is identical before and after (see results file).
3. Checkpoint. save_checkpoint writes adapter_checkpoint.npz
   plus a JSON sidecar (format tag, rank, alpha, scaling, and
   sha256 hashes of A, B, and the base). load_checkpoint verifies
   all three hashes and raises on any mismatch. The round-trip
   check in run_build.py reloads the saved adapter and rescoring
   gives exactly the after numbers (0.9141, loss 0.2032).
   The checkpoint files are run outputs, listed in .gitignore,
   regenerated by every run_build.py run.
4. Eval harness. evaluate returns loss, accuracy, correct count,
   per-class accuracy, and the 4 by 4 confusion matrix. After
   training, the weakest test class is class 0 at 0.8667 and the
   strongest is class 3 at 0.9623; before training class 3 was
   the weakest at 0.3774, which is most of the gain.

Training history is in the results file: validation accuracy
reaches 0.9375 at epoch 10 and ends at 0.9141 at epoch 60, so
the run mildly overfits after the early epochs and no early
stopping or best-checkpoint selection is applied. That is a
named limit, not a hidden one: the shipped checkpoint is the
final epoch adapter, scored as reported.

## The GRPO track (grpo_build.py)

Learn computed advantages and stopped. Build trains.

- Policy: one logit vector per prompt, 8 prompts, 4 actions.
  The reference policy is the initial policy, frozen.
- Task: each prompt has one correct action (2, 0, 3, 1, 2, 3,
  0, 1). The checker returns 1.0 for the correct action and
  0.0 otherwise. Verifiable by construction, and synthetic:
  it stands in for a math or code checker, it is not one.
- Objective per iteration: sample a group of 8 actions per
  prompt, compute normalized group advantages (same rule as
  Learn), then take 2 inner epochs on the loss: negative mean
  clipped surrogate (eps 0.2) plus beta 0.04 times the exact
  categorical KL to the reference policy. The gradient is the
  hand-derived tabular softmax gradient, with zero surrogate
  gradient for samples whose clipped branch is active outside
  the clip range.
- Result: fresh-sample mean reward 0.2070 to 0.9766, greedy
  accuracy 1 of 8 to 8 of 8, train group reward 0.2656 in the
  first iteration to 0.9219 in the last. Evaluation during
  training (separate eval seed stream) rises from 0.2734 at
  iteration 1 to 0.9297 at iteration 60. Final mean KL to the
  reference is 1.1795 nats: the KL term is priced in the loss
  at beta 0.04, it does not hold the policy near the reference
  at this beta, and the history table in the results file
  shows the KL growing steadily. A larger beta trades reward
  for closeness; that sweep is Deep scope.

## Failure modes

- Overfitting after early epochs: validation peaks before the
  final epoch and the pipeline ships the final adapter anyway.
  No early stopping, no best checkpoint selection yet.
- KL drift: at beta 0.04 the policy moves far from the
  reference (KL 1.1795). On a real run that is the drift the
  KL term exists to prevent; here it is measured and named.
- Zero advantage groups: when a group is all correct or all
  wrong, every advantage is 0 and that prompt gives no signal
  that iteration. Late in training, as reward nears 1.0, more
  groups saturate this way, which slows further learning.
- Reward hacking: none can appear on this checker, because the
  reward is the task definition itself. On a learned reward
  model the same loop could exploit the scorer. No reward
  model is used here, so no hacking check was possible or
  claimed; the Deep scope carries the failure log entry.
- Rank misspecification: the SFT gain depends on the true
  change being rank 2 by construction. A task whose needed
  change is not low rank would score lower at this rank, and
  nothing here measures that case.

## Honest limits

- Synthetic tasks and NumPy teaching models only. No real LLM,
  no real text or instruction data, no tokenizer, no open
  model run. The SPEC Build words "on an open model" are not
  met by this level; see BUILD-SPEC.md and the limits below.
- Scoring is this repo's own eval harness, not the P06 harness.
- One linear layer, no bias term, fixed learning rate, no
  optimizer state in the checkpoint, npz checkpoint format
  rather than safetensors.
- Run on the Muse VM, CPU, by this level's CPU teaching scale
  design, not on the BlackBox GPU node. BlackBox was verified
  on this cycle by the coordinator; no GPU step was due for
  this NumPy build, and the CPU location is a named limit,
  not a silent substitution.

## Limits named at review

- Synthetic tasks and NumPy teaching models, not a real LLM or real data.
- SPEC gap: GRPO on a toy tabular policy with this repo's own harness, not on an open model scored by the P06 harness.
- Run on the Muse VM CPU, not the BlackBox GPU node, by this level's CPU teaching design.
- True change rank 2 by construction in the SFT track.
- GRPO task is 8 prompts with a binary checker only, no reward hacking probe (Deep scope).
- One linear layer, no bias, fixed learning rate, no optimizer state in the checkpoint.
- Checkpoint in npz format, not safetensors.
